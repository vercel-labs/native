# How it works

```
index.html + style.css ──native──▶ .native/page.json (node table + pre-cascaded numeric rules, in the bundle)
app.ts ─────────────────────────▶ .native/src/     (copied; `document` import injected)
runtime/*.ts (DOM, style, layout, paint) ─┐
                                          ├──scriptc──▶ native binary
host/macos.m (window, events, CG/CoreText)┘   via FFI
```

**Build time (`native`):** parse HTML and CSS, parse every value into numbers, match tag/#id selectors, sort by specificity, merge unconditional rules per element, remove rules no element can match, and report unsupported features with hints. Every input the build reads is hashed first, and a build whose hashes match an earlier one reuses that build's executable instead of running scriptc; the cache is described in the [CLI reference](cli.md#build-cache). The page's tables are data rather than generated code, so an edit to the markup or styles changes nothing scriptc compiles: the build rewrites the tables file in the bundle and keeps the executable, in milliseconds. A change to the scripts, or to generated code the markup decides (an inline handler's element, a script's order), is a new program and still compiles. A rule is only removed when the page's scripts can't bring its selector to life: once a script touches `classList`, `className`, an `id` or an attribute (`setAttribute`, `dataset`, …), class and id conditions are left to the runtime, an id condition becomes an `[id]` test, and every rule is kept.

**Runtime (TS → native via scriptc):** class and `:hover`/`:active`/`:focus` checks for the remaining conditional rules, inline styles set from script (parsed with the compiler's own value parser, see `shared/css/`), inheritance, block and flex layout, text wrapping, painting, hit testing, focus, text editing, and event dispatch.

Elements created with `document.createElement` never went through the build-time cascade, so `native` also emits a compact selector table: every rule a created tag could match, already in cascade order. At runtime a created element only compares its tag and id against that table. `native` emits the table when your scripts call `createElement`, and it finds the tags involved by scanning the scripts for `createElement("…")` calls; when a script may change an existing element's classes or id, the table holds every rule instead, so a selector the build couldn't match statically can still start matching later.

**Bundles:** a build writes the app's files next to the executable so the app runs once moved and its source is gone. The compiler records every image, `@font-face` file, linked or imported style sheet, and the files scripts name with a literal `fetch()` or import; a `public` directory beside the page is the site root, so everything in it is copied too, at the app's root, and a URL a script builds at run time names one of its files. `compiler/bundle.ts` gives each a place in the bundle (the path it had relative to the app, so a page-relative URL still names it) and copies them into the `.app`'s Resources on macOS or a `<executable>.resources` directory elsewhere. The tables name the bundle-relative paths, and the runtime asks the host for the bundle's directory at mount, prefixing every file it opens (`runtime/assets.ts`). The bundle also holds `.native/page.json`, the compiled page and style tables: the executable carries none, so the same executable serves every edit to the page, and the runtime reads the file at startup (`runtime/app/page.ts`). A dev build skips all of it, keeps the source paths, and writes the tables to `.native/gen.ts` and `.native/dev.json` instead.

**Host (~300 lines of Objective-C):** window, event pump, a retained display list replayed with CoreGraphics/CoreText, and text measurement. The Windows host (`host/windows.cpp`) replays the same display list through Direct2D and DirectWrite on a Direct3D 11 swap chain. The headless Linux host (`host/linux.c`) paints it with Cairo and FreeType, and publishes the page's accessibility tree on the AT-SPI bus, where the macOS host publishes it through NSAccessibility.

## scriptc features in use

- **`Immutable<T>`** isn't used for now: with it, scriptc refuses apps that include untyped JavaScript (scriptc issue 9). The compiled tables are plain module constants until that's fixed.
- **FFI callbacks** (format 3+) carry typed text from the host back to TypeScript without string returns.

Known compiler gaps and their workarounds are in [compiler-limitations.md](compiler-limitations.md).

## Frontend frameworks

A framework ships as an npm dependency and builds the app's markup itself, so `examples/preact-todo` (Preact with hooks, no JSX) is the reference: it renders, takes typing and clicks, and updates its list, and `tests/preact.ts` drives it through `NATIVE_STEPS` in `pnpm test`.

- **Dependencies are vendored.** `native` resolves each bare import the way Node does (`import.meta.resolve`), copies the package's shipped source into `.native/src/deps/`, and rewrites the specifiers between copies. A copy is how a dependency's bare `document` and friends get bound to the runtime: the same global imports `native` adds to app sources are prepended to each copied file. Type-only imports keep resolving from `node_modules`, so their declarations still typecheck.
- **A package's declarations see the runtime's DOM.** A package that ships `.d.ts` files names the DOM the way a browser's `lib.dom.d.ts` provides it — `HTMLElement`, `HTMLInputElement`, `Event` — and a declaration is only as good as the DOM it is checked against. `compiler/dom-globals.ts` writes `.native/dom-globals.ts`, a generated module the entry imports, which declares each name from the runtime module that implements it, so a package's declarations are checked against the classes the app actually runs. The declarations are interfaces extending the runtime's, so they merge with the empty DOM interfaces a framework ships for projects without a DOM library (React's `global.d.ts`) rather than colliding with them. A name the runtime doesn't implement is left undeclared, and a declaration that needs it fails to type-check at the place that uses it instead of naming a browser API that would fail at run time.
- **The DOM is the framework's interface.** Nodes are real `Node`/`Element`/`Text`/`Comment`/`DocumentFragment` objects with the node API, every element carries the `on<event>` handler properties (a framework checks `"onclick" in el` to pick the listener name it registers), and attribute values may be booleans, as a renderer passes `disabled: true` straight through.
- **Updates land between frames.** A batched renderer commits from a resolved promise, so a step's effect is on screen before the next step reads it; work scheduled for the next animation frame (Preact's `useEffect`) runs on a `frame` step.
- **The DOM queries with the style sheets' selectors.** `querySelector(All)`, `matches` and `closest` go through the same selector engine the cascade does, so combinators, selector lists, `:not()`/`:is()`/`:where()`, attribute selectors and `:scope` select what a browser would, and an invalid selector throws a `SyntaxError`; see [supported.md](supported.md). `getBoundingClientRect` and `getClientRects` answer in viewport coordinates, and an inline box reports the runs of its fragments rather than a box of its own.

## Source layout

Big areas are split into small modules, so separate changes rarely touch the same file. The top-level file in each area re-exports its public API, so imports elsewhere don't change.

- `shared/css/`: the declaration and value parser, used by the compiler and by the runtime for inline styles: `declarations.ts` (declaration blocks, lengths, keywords), `colors.ts`, `borders.ts`, `fonts.ts`, `properties.ts`, and `properties/` with one module per area of CSS (`box`, `flex`, `borders`, `backgrounds`, `text`, `misc`). To support a property, add a case to its area's module.
- `compiler/css/`: `parse.ts` (style sheets, error recovery), `selectors.ts`, `types.ts` (selector types), `declarations.ts` (the declarations above, plus diagnostics) and `fonts.ts` (`@font-face` scanning).
- `compiler/bundle.ts` and `runtime/assets.ts`: the files a build copies beside the executable, each at its place relative to the app, and the directory the runtime finds them in at startup.
- `runtime/layout/`: `box-model.ts` (lengths and box sums), `text.ts`, `box.ts` (layoutBox dispatch and root), `block.ts` (block flow, margin collapsing), `inline.ts`, `flex.ts`, `geometry.ts` (offsets, scrolling into view), `positioned.ts` (absolute and fixed).
- `runtime/cssom.ts`: `el.style` (a `CSSStyleDeclaration` subset), the `style=""` attribute, the computed-style object and `getComputedStyle`.
- `runtime/app/`: `mount.ts` (compiled tables, frame pipeline), `page.ts` (reads a release build's tables from its bundle and mounts them), `dev.ts` and `dev-watch.ts` (a dev build's in-place table reloads and the files they read; not compiled into release builds), `pointer.ts`, `scroll.ts`, `keyboard.ts` (keys, text editing), `dnd.ts` (the drag lifecycle and a drop of files from outside the app), `loop.ts` (native event loop), `headless.ts` (`NATIVE_STEPS`/`NATIVE_SNAPSHOT`, `run()`).
- `runtime/clipboard.ts` and `runtime/editing.ts`: `navigator.clipboard` and the `ClipboardItem`s it reads and writes (the host owns the pasteboard), and the copy, cut and paste events with the commands `document.execCommand` runs. The events carry a `DataTransfer`, so a handler sees and replaces exactly what the clipboard gets.
- `runtime/composition.ts`: the marked text an input method composes into a text field, the value and selection changes it makes, the composition and input events it fires, and the caret rectangle it hands the host for the candidate window. `host/macos.m` routes keys through `NSTextInputClient` and reports composition phases to the runtime as `EV_COMPOSE`.
- `runtime/indexeddb.ts` and `runtime/sqlite.ts`: the IndexedDB factory, databases, version changes, transactions and object stores over a small binding to the host's SQLite. The Linux and macOS hosts (`host/linux.c`, `host/macos.m`) link the system sqlite3 and the Windows host (`host/windows.cpp`) links Windows' own `winsqlite3.dll`, through the import library a build makes from `host/vendor/winsqlite3.def`; each keeps the open databases and statements the binding names by id, and each database is a file under the app's data directory.
- `runtime/window.ts` holds the window's own members — opening another window, the handles on one, messages between them, its frame and fullscreen, and its events — and `runtime/menus.ts` reads the page's menu markup into the menu spec the host builds and runs the commands a menu item asks for. The host side (window, menus, the pipes between windows) is in `host/macos.m`; the Linux host records the same requests for headless runs.
